# Zemlo — Auditoria global de completude + roadmap priorizado

**Data:** 2026-09-20
**Âmbito:** todo o repositório (`apps/api`, `apps/web`, `packages/shared`) contra a
especificação que o próprio projeto mantém (`README.md`, `docs/`).
**Modo:** leitura apenas. **Nenhum ficheiro de código foi alterado.** O `git status`
continuou com os mesmos dois itens untracked do início (`.\workbuddy-ai/`,
`apps/web/src/styles/import.css.part`) e `HEAD` continuou em `8184939`.

---

## 0. Sumário executivo

O Zemlo está **muito mais completo do que incompleto**. A API tem 97 endpoints, 29 modelos,
32 rotas de interface e 1276 + 74 testes verdes. O que falha não é o núcleo — é a
**última milha**: capacidades que existem no servidor e não chegam ao utilizador, e
garantias operacionais que ainda não existem.

Três conclusões que mudam prioridades:

1. **Não há caminho de recuperação de password para o utilizador.** Os dois endpoints estão
   implementados e testados, mas não há ecrã, e o link só vai para o log. Quem se esquece da
   password fica permanentemente excluído. É o único defeito desta auditoria que
   **inutiliza a conta** — exatamente a classe que `DECISIONS.md` A22 e A23 dizem ter sido
   criada para eliminar.
2. **A cobertura de testes é quase toda de importação.** 20 dos 24 ficheiros de teste da API
   são sobre import/export. `auth`, `vehicles`, `expenses`, `documents`, `reminders` e
   `compliance` **não têm um único ficheiro de teste** — são cobertos só pelos scripts
   `verify*`, que não correm em `npm test`. O número "63 unitários" do README está desatualizado
   (são 1276) e esconde esta concentração.
3. **A documentação e o código divergiram em três pontos concretos**, todos originados por
   trabalho recente bem feito: a A17 diz que os bytes dos documentos não são guardados, mas
   são; o README diz 27 tabelas, o schema tem 29; e a interface de documentos afirma que a
   API não transmite bytes — verdade, mas por uma razão diferente da que o texto sugere.

O roadmap (§7) prioriza por **risco de dano ao utilizador**, não por esforço nem por
elegância.

## 2. Lacunas que deixam o utilizador sem saída

### 2.1 Recuperação de password — **bloqueante para abrir a plataforma**

| | |
| --- | --- |
| **O que existe** | `POST /auth/password-reset` e `/confirm` (`auth.ts:126,142`), tokens de uso único, expiração 60 min, hash SHA-256, revogação de todas as sessões |
| **O que falta** | (a) qualquer ecrã em `apps/web` — `grep -rn "password-reset\|Esqueci\|forgot" apps/web/src/` devolve **zero**; (b) entrega real de email |
| **Prova do segundo** | `setEmailSender` (`email.ts:68`) **não tem um único chamador em produção**. Só `sendEmail` é usado (`auth.ts:531`). O remetente é sempre o no-op, pelo que o link fica no log |
| **Já diagnosticado pelo projeto** | `OPERATIONS.md` §3.4.1 di-lo sem rodeios: *"não serve para utilizadores reais: quem se esquecer da password não recebe nada"* |

O texto de `OPERATIONS.md` já identifica a correção exata: *"implementar `EmailSender` em
`services/email.ts` e registá-lo com `setEmailSender`. Nada do fluxo de tokens precisa de
mudar."* A auditoria confirma que essa avaliação está **correta** — a lacuna é de ligação,
não de desenho.

**Impacto:** conta permanentemente inacessível. É o único defeito encontrado com esta
gravidade.

### 2.2 Documentos: o ficheiro nunca chega ao utilizador

| Operação | Estado |
| --- | --- |
| Criar metadados | ✅ `POST /documents` |
| Listar / ver metadados | ✅ `GET /documents`, `GET /documents/:id` |
| Editar metadados | ✅ API (`PATCH /documents/:id`) — ❌ **sem UI** (`queries.ts` não tem `updateDocument`) |
| **Carregar o ficheiro** | ❌ não existe endpoint de upload; a UI pede uma `storageKey` **escrita à mão** (`DocumentsPage.tsx:168`) |
| **Descarregar o ficheiro** | ❌ não existe endpoint; `DocumentStorage.read()` tem **um único chamador** — `export-bundle.ts:496` |

O ponto fino: **o sistema já é capaz de ler os bytes**. A capacidade existe e funciona — só
é exercida pelo exportador do bundle. Servir um documento é, por isso, uma tarefa
**pequena e bem delimitada**, não uma reescrita.

Isto contradiz três textos ao mesmo tempo:

- `DECISIONS.md` A17: *"No MVP não serve os bytes"* — verdade sobre HTTP, **falso** sobre
  armazenamento: os bytes são gravados e viajam no bundle.
- `DocumentsPage.tsx:110`: *"não o ficheiro em si… esta versão da API não os transmite"* —
  tecnicamente defensável, mas ficou desatualizado face ao trabalho de import/export.
- `OPERATIONS.md` §9: *"os bytes vivem num armazenamento de objetos, que ainda não está
  configurado"* — **falso**: `LocalDocumentStorage` está implementado e testado (25 testes).

### 2.3 `/records/:kind` degrada em silêncio para despesas

`RecordsPage.tsx:337` faz fallback para a configuração de despesas quando o `kind` não está
em `RECORD_CONFIG` — que só contém `expenses`, `fuel`, `charging`, `maintenance`. Mas os
seguros, inspeções e impostos **existem** na API e na UI (como separadores em
`VehicleDetailPage.tsx:802,927,1057`).

Resultado: `/records/insurance` não dá erro — mostra o **ecrã errado**. Uma degradação
silenciosa é pior do que um 404, porque o utilizador não sabe que está no sítio errado.

## 3. Código e modelos sem consumidor

### 3.1 Seis modelos declarados e nunca usados

Verificado por `grep` exaustivo em `apps/api/src/`: **zero** referências (não só nenhuma
chamada — nenhuma menção).

| Modelo | Nota |
| --- | --- |
| `Household`, `HouseholdMember` | Famílias (§32) — A18 é honesta: *"Nada disto é exposto na API"* |
| `Organization`, `OrganizationMember` | Frotas (§32) — idem |
| `AppSetting` | Sem qualquer leitura/escrita |
| `HomeAssistantEntity` | A especificação HA é **calculada em tempo real** (`integrations.ts:246`), nunca persistida |

O `README` agrupa isto como *"modelo **e especificação** prontos, sem ligação"*. O **modelo**
está pronto; a **especificação** não existe como documento para famílias/frotas. É uma
generosidade de linguagem, não um defeito — mas convém não a ler como "meio caminho andado".

### 3.2 O motor de migração de bundles nunca correu

`domain/import/migrate.ts` (440 linhas) tem `migrateBundle`, `runMigrations`,
`findMigrationPath` e `MIGRATIONS`. Só `checkCompatibility` é importado (por `bundle.ts:55`);
**todo o resto é exclusivo dos testes** (`import-plan-migrate.test.ts`, 150 testes).
`MIGRATIONS` é um **array vazio**.

Com `FORMAT_VERSION === MIN_SUPPORTED === 1`, o ramo de migração é inalcançável. É
andaime para o futuro, não código morto por acidente — mas é 440 linhas que nunca correram
a sério, e isso deve constar como risco caso se suba a `formatVersion`.

### 3.3 Notificações que nunca disparam sozinhas

Não existe agendador: `grep -rn "setInterval\|node-cron\|cron(" apps/api/src/` → **vazio**.
`syncNotifications` só corre como efeito lateral de abrir o dashboard (`insights.ts:148`).

Para o MVP isto está assumido e documentado (`OPERATIONS.md` §9: *"para o MVP é
equivalente"*). Vale registar a consequência honesta: **um lembrete legal não avisa
ninguém enquanto ninguém olhar**. Para inspeções e seguros, isso é uma diferença material
face à promessa do produto.

## 5. Cobertura de testes: a concentração

Este é o achado estrutural mais importante da auditoria.

```
apps/api/test/ — 24 ficheiros
├── 20 ficheiros .................. import / export / zip / document-storage
└──  1 ficheiro .................... domain.test.ts (lógica pura)
    (os outros 3 são helpers/config)
```

**Não existe um único ficheiro de teste para:** `auth`, `vehicles`, `expenses`/`financial`,
`documents`, `reminders`, `notifications`, `compliance`, `analytics`, nem para nenhum
módulo de `http/routes/` fora da importação.

Essas áreas **são** verificadas — por `verify.ts` (231), `verify:auth` (35),
`verify:regressions` (70), `verify:integration` (28). Mas esses scripts:

- exigem **servidor a correr** (`ECONNREFUSED 127.0.0.1:4000` sem ele);
- exigem uma **base de dados real e semeada**;
- **não correm em `npm test`** nem, portanto, em qualquer verificação automática de commit;
- são sensíveis ao ambiente (a armadilha do `DATABASE_URL` e o rate-limit de 20/15 min que
  documentei em `8184939` produzem **falhas falsas** em cascata com assinatura de 401).

Isto explica exatamente o padrão que o próprio README descreve: três defeitos graves
passaram 223 verificações e só apareceram em revisão manual. A classe de defeito não foi
eliminada — foi movida para um lugar onde não é executada automaticamente.

**Consequência prática:** um commit que parta o `auth` passa `npm test` a 100%.

## 7. Roadmap priorizado

Ordenado por **risco de dano ao utilizador**. O esforço é indicado, mas não decide a ordem.

### P0 — Desbloqueia utilizadores reais

| # | Tarefa | Porquê P0 | Esforço | Evidência |

## 8. Confiança e limites desta auditoria

**Alta confiança** (verificado por leitura direta de código e `grep` exaustivo):
ausência de UI de recuperação de password; ausência de endpoint de bytes de documentos;
os seis modelos sem consumidor; ausência de agendador e de CI; a contagem de 29 modelos,
32 rotas e 97 endpoints; a concentração de testes (20/24 sobre importação).

**Média confiança:** o impacto visual exato do fallback de `/records/:kind` (confirmei o
ramo de código, não renderizei o ecrã); a completude de estados no `HomeAssistantPage`.

**Não determinado:** se helpers "sem consumidor" em `domain/` (como `formatEnergy`,
`consumptionLabel`) são código morto ou superfície deliberada para o cliente mobile futuro.
O README invoca um contrato partilhado; nesse caso a superfície faz sentido. **Não os
classifiquei como defeito** por essa razão.

**Método:** auditoria por leitura de código e verificação documental. Os números de teste
foram confirmados por execução (`1276` API, `74` web). Não foi executado nenhum comando que
escreva no repositório.

## 9. Recomendação

Fazer **P0 antes de qualquer outra coisa** — em particular o email, porque é a única lacuna
que deixa um utilizador sem saída e a correção já está desenhada. A seguir, o CI (#4), porque
transforma a disciplina manual em garantia e é o que impede que os defeitos do futuro se
escondam onde os de hoje se esconderam.
